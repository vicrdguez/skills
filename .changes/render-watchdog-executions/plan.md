# Deliver Tailored Watchdog Executions Plan

## Approach

Use ADR 0001's execution-specific refinement and the shared rendering/resource mechanism delivered by `render-deferred-resources`. Move deterministic specialization into the engine's typed review situation, not into worker assembly or prose inference. Compose a complete review procedure, then add only narrow post-preparation instructions for facts startup cannot establish. Render outcomes from the verified engine result, never by rerunning the operation.

The sole native Dependency is `render-deferred-resources`; there is no dependency on the implementation-rendering sibling. #40 is an external transitive prerequisite. The user approved publication before it merges with an advisory `Blocked by #40` note on the first child issue, not a new native edge on this slice. Before implementation, include the merged prerequisite code and inspect its final interfaces. The starting main commit `c691fdf` already includes #37/#39 and the confirmed #44 ADR refinement, but not the #40 startup correction. This prerequisite integration is not adoption of ADR 0005's general pre-Audit integration rule.

Keep one coherent delivery: its review burden is instruction completeness, fixed review identity across deferred facts, safe evidence delivery, verified outcome presentation, and discovery/cutover. Use representative review contexts and focused failure cases rather than a Cartesian suite or a parallel behavior redesign.

## Implementation decisions

- `next` and `resume` deliver the complete Execution Skill as Markdown by default; `submit` delivers a Markdown verified outcome or applicable refusal. Explicit `--format json` exposes equivalent typed transport. Ordinary workers report in Markdown, not exact CLI passthrough. No Watchdog `start` alias is added.
- Validate presentation and execution-capability inputs before avoidable Workflow effects. Keep rendering downstream of a single operation result; it cannot acquire, publish, or retry. A nonzero error remains a failure, not a synthetic successful status.
- Engine facts explicitly describe the review situation and known references. Separate retained Review Count and completed-review history from a usable comparison range. Templates do not derive review mode from branch names, comment bodies, or incidental field combinations. Preserve an available previous review reference even when its object cannot establish incremental scope.
- A first review is full. Repeat scope is incremental when the retained prior head is available and ancestral, including an empty same-head comparison; otherwise it falls back to full while retaining count and findings obligations. Missing checkpoints start count zero without discarding supplied prior findings or allocating replacement W identities. The worker still interprets opaque finding ledgers and authorized directives; the renderer does not parse them into judgments.
- Preserve explicit resume semantics: a fresh resume invocation observes the selected Claim's current head and local progress without incrementing completed count. Once an invocation binds its reviewed head and round, later inspection cannot silently replace them. Already-started publication requires the original fixed-number command and Result Documents, not a new review. Preserve supplied artifact overrides on every applicable generated command; marker-resolved work gets no invented override flags.
- Startup uses repository/remote/worktree-location and selected-item/checkpoint metadata only. Even warm local objects do not authorize project-object, Git-log marker, ancestry, or historical-body inspection. Bind all established facts immediately; supply concrete safe Git preparation and later inspection/read instructions for what is unavailable. Do not fetch or create worktrees in startup.
- Reuse the merged prerequisite's inspection path and artifact/scope logic. Only if that path cannot supply necessary Watchdog-specific local facts, expose the smallest Watchdog inspection continuation; its command spelling and private layout are delegated. It must consume fixed invocation identity, return narrow specialized instructions or repairs, and avoid queue selection, Claim acquisition, new result allocation, and another full skill. Do not add it for lane symmetry.
- Historical ledger reads occur after preparation at exact resolved Baseline and Completion endpoints, including all ledger files. Preserve the active endpoint rules in `skills/dev/watchdog/SKILL.md`: unique marker resolution or explicit full SHAs; matching path sets and mode-100644 blobs; only permitted completion ticks; every automated box checked and Manual Verification unchecked; endpoint ancestry/reachability; ledger absent at reviewed and final heads. Intermediate history is not a substitute for endpoint evidence.
- Preserve the rest of that active Skill Definition and `reference/review.md`: caller freshness and single-item review, independent Full Gate, Audit-claim and test-strength verification, materialized frozen scenarios, stable finding IDs, human authorization/precedence, first-review batching, repeat regression/critical-class limits, and opt-in independent test reimplementation only when explicitly requested. No Audit invocation, functional fixes, automatic follow-up issues, or revised testing policy.
- After permitted Debt Markers, keep the original reviewed head for the review and anchors, record the actual pushed final head separately, and require the existing Post-Marker Check. Refresh local integrity facts affected by those changes before publication without substituting fixed invocation identities. Final PR bodies preserve Audit/review evidence and the Baseline's Manual verification section verbatim and unchecked. Engine identity checks do not assert verification of source comments, project checks, or human checks.
- Use the sibling's shared Go `text/template` composition for coherent common, first-review, repeat-review, and history-dependent procedures. Avoid per-paragraph fragment files or an additional renderer. Preserve once-only inclusion and Skill Resource ownership; private Skill Modules are not discoverable resources. Exact filenames and small helpers are implementation choices.
- Keep `reference/review.md` deferred until before dispositions. Its generated retrieval command uses the shared repeated `--input name=value` contract, binding every settled value used there, especially PR, round, original head, and result paths. Only later-known inputs remain agent-supplied and explained. A verdict cannot be required before disclosing the rules for choosing it; ordinary Result Document prose is never a rendering input. Use the sibling's typed validation and input-description contract rather than a new schema or saved invocation bundle.
- Show each already-fetched opaque PR body/Audit ledger and selected feedback record once, completely, in clearly delimited data sections with available provenance, association, timestamps, commits, and anchors. External strings, including Go template syntax and Markdown delimiters, are data rather than template source or trusted workflow instructions. Use the shared command-argument quoting for bound values. Safe framing must not change legitimate authorized-directive meaning or manufacture missing metadata.
- For evidence not delivered, generate selected-repository-bound `gh` commands for the PR body, source issue comments, PR discussion comments, review summaries, and inline comments. Use complete pagination for list streams and explicit failure/truncation handling. A successfully read empty stream is evidence of absence; an undelivered or failed stream is not. Rendering adds no network fetcher or startup hydration and does not request redundant reads of complete delivered evidence.
- Reuse known execution-capability input only for an already-supported applicable recipe. Unknown capabilities retain genuine runtime alternatives. Watchdog does not invoke Audit, so do not manufacture an Audit-style parallel recipe or change direct-invocation freshness from harness identity. If no Watchdog step varies with a capability, leave the procedure unchanged without adding capability-only flags or depending on the implementation-rendering sibling's plumbing.
- Preserve engine-owned review-limit routing and #39 observational, release-last recovery. Only verified publication and released Claim justify completed `ready_for_merge`, `rework`, or `needs_human` output. Failures retain exact available retry identities and Result Documents, distinguish known retained from uncertain Claim state, and never prescribe unauthorized release. Cleanup-only warnings after verified completion do not trigger republishing. Passing remains allowed beyond the default limit and despite conflicts; #37 leaves integration and merge to humans.
- Install Watchdog Skill Stubs that directly run `skl watchdog next`. Plain `skl skill watchdog` refuses with guidance without work selection; reasoning definitions and named Watchdog resources still work. Preserve marker-owned refresh and user-owned files across Pi, Codex, Claude Code, and OpenCode.
- Replace the marker-owned Pi Watchdog loop prompt with disabled stop-before-launch guidance using the existing installer path, so stale installed copies actually change. Keep the one-item runner with a normal Markdown report. Leave the implementation loop and `queue-next.mjs` usable while referenced; removing an unused helper is optional only when no callers remain, otherwise separate Pi work. Do not add a JSON compatibility relay or a sibling dependency.

## Module shapes & seams

### Modified: Watchdog command and outcome presentation

Interface: public in-process `skl watchdog next`, `resume`, and `submit`, plus only a necessary generated inspection continuation. Inputs include the existing selected repository/remote and fixed review arguments, presentation format, and only capability inputs needed by existing Watchdog recipes. Outputs are Markdown by default or explicit JSON with the same authoritative result. Dependencies are the existing Workflow Engine, backend adapter, shared renderer, and Git inspection logic.

Test through the existing `newApp(...).Run(...)` seam with backend/HTTP fixtures and temporary real Git repositories. Observe returned output, backend effects, checkpoint behavior through existing fixtures, Git preservation, and fixed commands. Reuse `cmd/skl/watchdog_test.go`, `watchdog_checkpoint_test.go`, `handoff_verification_test.go`, and `review_authorization_test.go`; update stale presentation expectations without weakening their behavior and failure-mode protection. Do not pin today's private fact structs, startup file maps, or helper call layout.

### Modified: Shared instruction delivery and Watchdog sources

Interface: instructions delivered by the workflow commands and public `skl skill --resource ... --input ... watchdog` retrieval, including the sibling's input description and validation. Dependencies are the common Go renderer and embedded authored sources. The module owns coherent composition, deferred disclosure, literal evidence framing, concrete commands, resource visibility, and once-only inclusion.

Use hand-authored complete representative output fixtures for first review, resumed progress, repeat incremental/unchanged-head, and full fallback, plus focused assertions for known-value binding, absent irrelevant branches, narrow inspection, deferred resources, evidence safety, and explicit JSON equivalence. Normalize only incidental temporary roots or fixture SHAs, not the instructions under test. Expected output must not be generated by the renderer being tested. Test instruction obligations as delivered content, not as a claim that tests prove future agent judgment.

### Modified: Harness installation and Pi entrypoints

Interface: `skl install` into temporary homes and following the installed Watchdog entry command. Dependencies are existing embedded stubs/prompts/runners and marker-owned refresh. Preserve user ownership, supported harness discovery, fresh-context responsibility, and one-item operation.

Extend the existing `cmd/skl/main_test.go` and `pi_test.go` installer tests to cover direct stubs, generic retrieval refusal, refresh of an old owned loop into disabled guidance, unchanged user files, and an independent implementation lane. Keep the existing queue-helper check while it remains referenced. No new harness runtime, test framework, benchmark, or evaluation seam is needed.

## Sequence

1. Confirm the native Dependency and transitive prerequisites are Merged, include their required code, and read their final renderer, startup, inspection, and recovery interfaces. Preserve the active pre-ADR 0005 contract.
2. Implement one named B scenario or outline per red-green cycle at the approved seams, beginning with the complete first-review rendering, then history/resume and metadata-only startup. Each outline is one table-driven behavioral task, not a cross-product suite.

4. Render verified outcomes, explicit JSON, input refusals, and no-work/wait results without new Workflow effects. Retain the existing authorization, convergence, and release-last regression protection.
5. Wire direct stubs and generic-retrieval refusal, refresh the owned Pi loop into disabled guidance, and preserve one-item reporting and the independent other lane. Update scoped documentation.
6. Run the focused and existing full checks, compare the representative complete renderings against the preserved active procedure, and complete only the existing ledger checkboxes. No scenario or contract prose is added or rewritten after the Artifact Baseline.
