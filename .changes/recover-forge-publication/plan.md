# Recover Forge Publication: Architecture

ADR0006 owns ledger authority, private reports, temporary public bodies, and latest-view publication. ADR0005 owns contract-grounded verification and construction freedom. These commitments define observable responsibility boundaries; exact new operation names, private types, file placement, and test organization remain delegated.

## A1: Add Explicit Recovery Beside Existing Normal Publication

**Module:** `cmd/skl` owns operator/agent CLI inputs and presentation. `workflow` owns selection of the latest pending local publication and deterministic preconditions. Consume the machine config, Project identity, private ledger, and normal acceptance/phase publication facilities already supplied through `run-ledger-delivery`.

**Interface:** Inspect pending publication and recover a selected issue or PR view through `skl`. Include initial parent/child issues from slice 1 and phase PR publication from slice 2. Distinguish local completion from external publication status in successful, already-satisfied, prose-needed, pending, stale, ambiguous, and repair outputs. Supply specialized Markdown by default and an explicit JSON option. This is an explicit bounded invocation, not worker selection, waiting, a loop consumer, or a background service.

At baseline, normal publication is visible in `workflow/proposal.go`, `workflow/handoff.go`, and `workflow/review.go`. Slice 2 separates their local handoffs from forge success. Reuse that resulting path rather than building another Implement/Watchdog engine or claiming normal publication as new recovery scope. Recovery cannot reset Claims, count, reports, Contracts, or Workflow State. The sole direct Dependency remains `run-ledger-delivery`, not the decision inbox or completion observer.

**Seam:** Public `skl` invocations over accepted proposals and completed phases in real local source/ledger Git repositories, with network failure supplied through the existing controlled forge HTTP seam. Verify preservation by CLI readback and committed Git contents rather than fake backend state alone.

## A2: Keep Latest-View Bookkeeping Separate From Prose and Execution

**Module:** The dependency's ledger persistence and publication coordination within `workflow` own pending metadata, exact input references, and forge attachments. Temporary Result Documents remain outside the ledger.

**Interface:** Bind recovery to the selected latest relevant acceptance/report/source inputs and known attachment. Reuse applicable available prose; otherwise return authoring instructions and references. Persist only the metadata needed to identify pending work, established attachments/effects, and current satisfaction, not `issue.md`, `pr.md`, an outbox body, every attempted presentation, or a separate publication event stream. Use explicit stored references, not arbitrary Git-history or commit-subject reconstruction. Read reports through the dependency's schema-1 boundary rather than reimplementing YAML interpretation or parsing verdicts from Markdown.

Serialize only brief local mutations. Validate the selected view before effects and compare it again before clearing pending information; unrelated ledger commits are harmless. When an in-flight external effect races a newer local result, preserve useful observed identity without declaring the newer view published. Reuse existing competing-history and replication safeguards. Do not promise a distributed transaction or hold a worker Claim or ledger lock while agents write prose or the network responds.

**Seam:** Real Git state observed through public recovery and private-read operations. Cover a current temporary body, lost body, stale body, unrelated commit, newer selected result before publication, and a newer result injected during controlled HTTP publication. Check latest-only catch-up and preservation of newer pending state and later Claims. No persisted-prose store or internal transaction-mock fleet is required.

## A3: Keep Forge Effects, Observation, and Draft Mapping in the Adapter

**Module:** The existing `setup.GitHubBackend` owns GitHub transport, repository binding, authentication reuse, object identity, readback, and draft conversion. Relevant current seams are `setup/github.go` (`CreateWorkItem`, `CreateCoordinationItem`, relationships, HTTP construction), `setup/implementation.go` (`PublishImplementation`, ownership checks, body updates, GraphQL draft conversion), and `setup/watchdog.go` (`PublishReview`, anchor handling, publication readback). `github/remote.go` supplies repository identity, not lifecycle authority.

**Interface:** Reuse or extend these adapter responsibilities for the latest issue/PR presentation. Reconcile ambiguous creates and partial effects by reading the selected repository and attachment before another mutation. A known lagging published source head may be caught up through slice 2's normal source-publication path when the exact inputs remain available and safe publication is established; observe the intended revision before presenting its approval. Refuse ambiguous ownership, duplicate candidates, invalid reviewed anchors, changed targets, unexpected or unestablished head changes, or unavailable required evidence rather than guessing. Do not force source updates or change code merely to republish. Observing a receipt can establish publication, never a Human Decision or workflow verdict. Optional selected inline findings use reviewed-code anchors and observable deduplication; full worker reports are not automatically sent through the existing review-comment path.

The adapter maps local pre-approval versus approved outcomes to GitHub draft/ready presentation. Do not add draft states to `workflow`, retarget existing PRs, or implement merge/closure reconciliation here. A merged/closed object encountered during recovery is a refusal or completion-observation handoff, not permission to mark local work terminal. `workflow/status.go` and `setup/status.go` expose the separate observer responsibility for slice 5; cleanup stays with slice 6. Reuse current token resolution and HTTP client injection; no new credential infrastructure. All production public writes remain `skl` operations, never direct `gh` mutation instructions.

**Seam:** Exercise the public CLI with `setup.NewGitHubBackend` and the existing controlled HTTP server/transport patterns. Cover both issue and PR lost-create responses, known attachments, expected source-publication lag and safe catch-up, partial body/draft effects, repeated recovery, unexpected identity/head/target conflicts, unobservable effects, closed PRs, and explicit inline selection. Assert observable request bodies, mutation counts, readbacks, and unchanged authoritative ledger facts. Do not test draft behavior only via an internal stub or require live GitHub writes.

## A4: Deliver Agent-Authored Public Content Through Existing Skill Resources

**Module:** `catalog.go`, `resource.go`, `distribution.go`, and existing authored `skills/dev/propose`, `skills/dev/implement`, and `skills/dev/watchdog` resources own specialized instructions and human-facing Result Document guidance. Extend this delivery path as needed for recovery; no parallel prompt renderer or prose generator.

**Interface:** When applicable temporary content exists, return the concrete recovery path using it. When it is missing or stale, supply current task facts, exact private evidence references, private retrieval operations, and a bound `skl` continuation. The agent authors a new descriptive issue, progress body, or Final Review Package rather than recovering identical lost bytes. Preserve deferred-resource behavior and bind known arguments; do not make the agent navigate or edit ledger files.

Guidance must distinguish private Contracts/full Phase Reports from public commitments, progress or outcome, useful verification, risks, and appropriate human checks. Complete Manual Verification remains accessible privately and human-owned even when the public version omits operational details. Optional actionable inline findings are explicitly selected and anchored, not an automatic report export. Do not invent an engine-side prose-quality or privacy classifier; prove the absence of automatic private-report publication and inspect the delivered instructions instead.

**Seam:** Rendered execution outputs and named resources retrieved through public `skl`, checked for exact references, current-view specialization, concrete continuation, privacy/manual-obligation guidance, and no direct forge-write or ledger-edit instructions. At the HTTP seam, distinctive private evidence absent from the supplied public body must not be automatically appended. Ledger inspection confirms no durable public-body snapshot. These checks validate shipped instructions and transport, not arbitrary agent prose quality.

## A5: Verify Recovery at Public, Stateful Boundaries

Use the repository's existing Go testing tools, real temporary source and ledger Git repositories, isolated config, and controlled forge HTTP seam. Existing public-HTTP patterns in `cmd/skl/decision_authorization_test.go`, `handoff_verification_test.go`, `completed_review_test.go`, and `watchdog_test.go` cover lost responses, protected later work, and inline anchors; reuse relevant fixture capabilities without preserving their superseded forge-authority or checkpoint assumptions. Do not add mock implementations for every internal interface or a new framework.

Group evidence many-to-many: acceptance/phase catch-up and latest-only behavior cover B1-B3 with A1/A2/A4; ambiguous effects and stale/racing requests cover B4-B5 with A2/A3; draft and privacy/inline checks cover B6-B8 with A3/A4. Every rule, scenario, and architectural commitment must be accounted for in the Submission's Verification section with concrete tests, commands, inspection evidence, results, and material limitations. These groupings do not prescribe one test per scenario, test-writing order, or a duplicate review suite. Changed failure handling requires demonstrated regression sensitivity under controlled HTTP faults.

Run the normal Full Gate and preserve independent Watchdog Review; Go checks include `go test ./...` and `go vet ./...` under the repository's verification at implementation time. No live forge account, mandatory human verification, agent-evaluation infrastructure, or duplicate `tasks.md` is needed. Implementation remains free to choose the smallest adequate structure while preserving these authority, privacy, and recovery boundaries.
