# Make Review Checkpoints CLI-Owned Plan

## Approach

Implement approved slice 3 on the local `2f68e43` baseline, which includes the opaque-ID/publication-binding correction from #32. There are no blocking Dependencies. Follow `CONTEXT.md`'s Review Checkpoint and Review Count definitions, the planned candidate-first capability, and ADRs 0002 and 0004. Deliver checkpoint protocol, scope, counting, and the minimum completion integration as one vertical slice: splitting these would leave two authorities for the same review.

The existing Workflow Engine remains the deep module. Put checkpoint mechanics behind its existing start/submit interface, use ordinary Git and filesystem operations internally, and keep GitHub publication in the existing adapter. No storage interface, repository abstraction, new backend, or general transaction module is needed. Opaque Work Item and Submission identities stay opaque; CLI numeric rendering remains in `setup/presentation.go` and command integration.

## Implementation decisions

### Selected worktree and checkpoint protocol

- Resolve the selected Work Item's dedicated worktree using the existing selection/worktree facts, independently of the invoking directory. Resolve its private Git directory with `git -C <selected-worktree> rev-parse --absolute-git-dir`; join `.watchdog` there. A linked worktree's `.git` is a file, not the directory to append to. Do not substitute `--git-common-dir`, invent a per-PR registry, or fall back to the main worktree. Failure to resolve an expected selected worktree is actionable; object-free startup remains slice 5.
- The sole retained record is `<count>:<sha>`: a nonnegative decimal count and a full hexadecimal commit SHA, with at most one terminal newline. Reject empty existing files, missing fields, negative/nondecimal/overflowing counts, abbreviated/nonhex SHAs, extra fields, and trailing data. Use the repository's full object-ID width. A syntactically valid SHA whose commit is unavailable is valid checkpoint data, not corruption.
- Only file absence means count zero/full scope. A valid zero count also means full scope. A permission/read error is not absence. Increment overflow is an actionable refusal, not wraparound or reset.
- Validate all inputs before publication. Write a complete replacement in the same private Git directory and atomically rename it over `.watchdog`; close/check write errors and remove an unused temporary replacement on handled failure. A temporary file for atomic replacement is not another persistent metadata record or recovery source. Do not truncate the live checkpoint, keep a backup, or add a second metadata file.
- Store only the latest completed review. No start/resume write, in-progress head, timestamp, verdict, Claim Token, or per-round history belongs in this file. The policy limit is separate from representation, defaults to two, and needs no new configuration surface in this slice.

### Invocation facts and review scope

- `StartWatchdog` captures the actual current selected PR head for this invocation and verifies it has not changed while preparing the packet. `resume` refreshes that observation, not a hidden persisted pin. Previously issued packets retain their original meaning; new facts cannot retroactively attest that an old worker reviewed a newer head.
- Supply completed Review Count, intended Review Number, explicit full/incremental scope, the current reviewed head, and a usable prior comparison only for incremental review. Count zero, a missing checkpoint, an unavailable prior commit, or a nonancestor requires full scope. Preserve any valid nonzero count on fallback. Equality is valid ancestry and permits a repeat review with an empty code diff.
- Scope governs code comparison, not whether the worker reruns the Full Gate, checks the historical artifacts, verifies active findings, or scans the whole for critical defects. Full fallback must not retain contradictory incremental-only instructions.
- `setup/presentation.go` generates the concrete command, including selected worktree/remote/item, `--review-number N`, `--reviewed-head H`, and absolute summary path. The worker adds the semantic verdict, optional anchors, pass body, and optional final head using the existing interface. For an uncompleted review N is C+1; do not derive N again inside submit.
- Preserve this exact command and its N in the original packet or caller-retained command context before publication. Existing summaries retain their ordinary review-round and reviewed-SHA facts, but do not add machine-specific submission commands to public feedback solely for recovery. Retained Result Documents provide the original supplied bytes; no extra packet file or metadata file is introduced. A new same-SHA round uses its own N; if the original invocation inputs are lost or ambiguous, stop for inspection rather than reconstructing a journal from prose.
- A normal interrupted review can resume with current head plus the last completed checkpoint. A partial publication is different: do not issue a fresh N=C+1 as if the recorded review were unfinished judgment. Direct replay of the original fixed-number command; if available facts cannot establish which operation is pending, stop for inspection. Neither a number recovered by parsing prose nor an inferred in-progress pin is a substitute.

### Completion and retry protocol

Here C is the stored count (zero if absent), P its completed reviewed SHA, N the explicit intended number, H the actual reviewed SHA from the worker's invocation, and F the optional final head. Review completion is recorded after all required evidence is durably observed, even if its subsequent workflow handoff is interrupted. That handoff interruption must not count as another review.

1. Validate N as a positive, nonoverflowing integer and H/F as full SHAs. Resolve the selected worktree and read/validate the checkpoint. Observe the selected Work Item, its Claim/state, current PR/local/pushed heads, and any already-published effects. Preserve current artifact and head guards.
2. Establish whether this is an admissible new completion or an exact retry. A new review uses N=C+1 under its selected review Claim. N=C is only a retry of the recorded H with matching exact publication observations, never a second increment. N<C, N>C+1, different H at N=C, incompatible verdict/evidence, or a later-stage Claim requires refusal. A missing checkpoint after verified `done` is a completed-publication case, not permission to start another review.
3. Choose the review-policy result from the semantic verdict and fixed N: rework at N<2 gives Rework; rework at N>=2 gives Needs Human; explicit Needs Human remains Needs Human; pass passes the review-count policy at any N. Apply remaining target/conflict policy independently and do not restore any resume-state persistence already removed by slice 4. Retrying N=1 after `1:H` was written must still produce its original first-failure Rework, not re-evaluate it as failure number two.
4. Publish/observe the complete opaque summary and inline evidence and, on pass, the final PR body through the existing adapter. Preserve its ordering where compatible with the invariant. Exact observations mean the supplied summary bytes, inline bytes plus commit/path/line/side, final body including closing footer, compatible disposition/projections, and current selected head/Claim facts. Neither label state alone nor any comment containing the same SHA proves this review. Reuse exact effects after lost responses; uncertain reads stop before checkpoint or Claim mutation.
5. Once all evidence is observed and guards still hold, atomically replace the checkpoint with N:H. If it already equals N:H, exact retry observations authorize leaving/replacing the same value, never incrementing it. A storage failure retains `wip` and Result Documents. A later handoff failure does not roll back an already recorded review.
6. Complete the existing destination/source projection changes and release `wip` only after checkpoint success. On a fresh invocation after a crash, the original command supplies N and original inputs, the checkpoint proves the recorded number/SHA, and exact published observations prove reusable effects, not ownership of a remaining Claim. Finish a claimed partial handoff only when surviving observations independently establish its source-stage protection. In particular, target-only `wip` after source cleanup may belong to a later stage; preserve it and stop if that possibility cannot be excluded. There is no local stage journal or promise of recovery at every interruption point.
7. Read back the completed unclaimed destination. Preserve the checkpoint for Rework and Needs Human, including a pass diverted to Synchronization Rework by the still-current target policy. Delete it only after verified `done` publication, not merely because verdict was pass or a `done` label briefly overlaps `review`/`wip`. Cleanup of checkpoint or existing private results after verified completion returns success with an actionable warning, not a failed verdict or republish instruction. An exact completed retry remains a no-op when that completion can still be verified; unavailable evidence requires inspection rather than reconstruction.

The fixed round is an operation input, not exclusive ownership, a nonce, or a lifecycle Claim Token. V1 retains its single-operator assumption. Exact receipt observations are existing published effects, not a new receipt file or engine-parsed review-summary schema. Packet/result retention makes the ordinary retry expressible; loss or contradiction of that context deliberately limits automatic recovery.

### Reviewed head and Debt Marker safety

Keep `--reviewed-head H` as an immutable input for the actual review and `--head F` as the optional final pushed revision. Without F, current local/remote/PR heads must equal H. A different F is legal only on pass, must descend from H, and must match those heads under repeated guards. Checkpoint H even if the final PR head is F. The worker alone verifies that post-review changes are nonfunctional Debt Marker comments and runs the Post-Marker Check: record final head, existing formatter/parser for touched files, and `git diff --check`. Preserve Full Gate ownership and do not introduce a CLI source parser, attestation record, or automatic project checks.

### Narrow ownership changes

- In `setup/implementation.go`, remove emission and consumption of `WatchdogHead`, `ReviewedHead`, and `ReviewRoundHead` hidden metadata fields and their fixed-pin guards. Existing comments need not be deleted or migrated; stale fields do not override fresh invocation facts. Other metadata, including target, resume-state, and transition fields, stays under its owning slice.
- In `workflow/implement.go`, remove previous-review extraction/refusal and the required available-ancestor cache, including corresponding command/fact presentation. Finding-driven Rework uses current branch code, historical ledger snapshots, and supplied feedback. It neither reads nor repairs the Watchdog checkpoint as an implementation prerequisite.
- Change `skills/dev/implement/SKILL.md` and `skills/dev/audit/SKILL.md` only where rework requires the previous review's cached SHA/diff baseline. Use an explicit caller fixed point when supplied, otherwise the ordinary PR comparison; keep work focused on findings rather than broad unrelated cleanup. Preserve both Audit axes and all artifact and gate obligations.
- Replace bounce-count use in `workflow/watchdog.go`, `workflow/review.go`, `catalog.go`, and presentation with completed-review facts. Remove only count computation and dead count-only variables from `setup/watchdog.go`'s timeline loop. Its `PendingReview` reconstruction remains until slice 4; do not turn this slice into a ban on every timeline request.
- `workflow/status.go` is another caller of `CompleteReview`. It must not consume a new round, infer N from timeline labels, or release a pending review without sufficient evidence that its checkpoint obligation was satisfied. When it lacks the fixed submit context, preserve the pending work and direct that submit retry. This is only the checkpoint-before-release guard, not a redesign of general handoff reconstruction. Independent existing status conflict diversion is not a new Watchdog Review and must not require a new round or recreate a checkpoint after verified `done` cleanup.
- Preserve slice 2's current target/conflict decisions until Merged; a newly completed conflicting pass counts once but may still divert. Preserve slice 4's other journal/metadata and partial-handoff policies, and slice 5's startup preconditions. No artifact-marker changes from slice 1 belong here.

### Module shapes and seams

#### Modified: Workflow Engine and CLI

Interface: existing `StartWatchdog` and `SubmitWatchdog`, exposed by `skl watchdog next|resume|submit`; submit adds the explicit review-number input. Existing implementation next/resume and status participate only in the narrow ownership changes above. `WatchdogFacts`, `BuildPacket`, and `PresentImplementation` carry the corresponding structured and rendered facts consistently. Keep mechanics behind this interface so every caller gets the same count/scope/retry rules.

Dependencies: existing Git commands and filesystem provide concrete local evidence/storage; existing `ReviewBackend` provides external publication observations. Use small private functions only where start/submit genuinely share checkpoint mechanics. No injectable checkpoint repository or private-function test seam is approved.

Test strategy: B1-B16 run through `newApp(...).Run(...)`. Reuse `proposalRepository`, `prepareSlice`, and Git helpers from `cmd/skl` where they match real linked-worktree needs; create actual dedicated worktrees rather than assuming the test process's checkout is the selected one. Observe CLI JSON, rendered packet, GitHub-visible effects, and later scope/dispositions. File location/format assertions are permitted because this storage behavior is an explicitly specified interface, but they do not substitute for operational results.

#### Modified: GitHub adapter

Interface: existing `ReviewSubmission`, `PublishReview`, `CompleteReview`, and implementation observation/Claim methods. Preserve opaque Result Document transport, exact body/anchor rereads, and numeric provider representation at this seam. Any necessary observation data belongs on these existing records, not a new journal service. Review Count comes from Git, not GitHub timeline history.

Dependencies: the existing HTTP client/endpoint seam is the controlled external dependency; Git is real in fixtures. Instantiate `setup.NewGitHubBackend` through `newApp`'s existing backend factory and serve observations/mutations with `httptest`. Do not prove retries by calling private workflow helpers or replacing completion/publication with a memory fake. Existing `setup/watchdog_test.go` HTTP response patterns are references, not the new acceptance entrypoint.

Test strategy: table-drive verdicts, evidence faults, storage faults, and handoff phases under the 16 scenario headings. A server may apply a mutation then lose its response, fail a read, or fail the first handoff request after checkpoint replacement. Storage permissions/rename conflicts are real filesystem faults; assert the injected fault actually occurred. Restart the app with retained Result Documents for crash retries, without preserving private in-memory workflow state. At Claim release, verify complete published evidence and N:H already exist; after faults, prove the subsequent packet/disposition and retry behavior. No new test-only production hooks are required.

## Sequence

1. Implement each B task as one red-green cycle at the approved CLI/HTTP seam, starting with worktree selection and packet facts, then counting and ordered completion.
2. Cover fault/retry paths with the original concrete command across fresh app invocations before removing the old review metadata/count authority.
3. Verify Implement/Audit guidance, status callers, target-policy independence, nonterminal retention, and accepted worktree-loss reset through the remaining B tasks.
4. Run `go test ./...` and `git diff --check`; update the relevant packet expectations and existing tests that asserted replaced behavior, without broad test refactoring.
5. Finish with the capability documentation task, recording only this slice as implemented and leaving the other candidate-first corrections planned.
