# Embed skill definitions behind common filesystem stubs

Author harness-independent skill definitions and their named resources as Markdown in the Workflow Definition Repository, embed them in the versioned Workflow Engine binary, and install only thin filesystem stubs for discovery. At invocation, the engine deterministically specializes a definition from structured facts and can return equivalent rendered Markdown or typed JSON; it does not infer, summarize, or ask a model to tailor instructions. This keeps one authoritative behavior across harnesses while preserving their static discovery mechanisms without depending on plugin packaging formats.

## Consequences

- Every invoked skill incurs one CLI call after harness activation.
- Pure reasoning skills gain centralized distribution but usually receive unchanged instructions and no context reduction.
- Stub installation and binary versions must remain compatible.
- Supporting resources are embedded and retrieved by name instead of being injected into every instruction packet.
- Skill Definitions guaranteed for an invocation are bundled once and listed in the packet manifest; conditional dependencies remain deferred, and adapters do not activate stubs already listed in the packet.
- Harness-specific execution capabilities remain outside the shared skill definition unless selected through deterministic adapter metadata.
- Pi, Codex, Claude Code, and OpenCode receive equivalent skill discovery and one-item workflow operations in V1; automated queue draining may remain Pi-only.
- V1 installs the binary from this repository with Go. The binary then writes its embedded common Skill Stubs into the supported Pi, Codex, Claude Code, and OpenCode user skill directories. OpenCode uses `~/.config/opencode/skills/<name>/SKILL.md` without cross-harness discovery dependencies or configuration migration; prebuilt releases, plugin packages, automatic updates, and uninstall machinery are deferred.
- Installation may also write harness-specific queue adapters where supported; deterministic Setup is a CLI command and has no Skill Stub.
- Skill templates use Go `text/template` with typed inputs and a deliberately small helper set; Consumer Repositories cannot override them in V1.
- Agent-authored handoff results use template-guided Markdown files in private temporary directories rather than command-line prose or tracked files. The CLI passes their contents through without parsing or validating the Markdown.
- A semantic command or typed flag carries each agent-decided outcome independently of its opaque Result Document. The engine validates and applies the requested transition but does not cross-check the decision against the prose.
- Packets and stubs carry protocol versions; compatibility guarantees begin at V1.
- The binary is named `skl` and exposes stage-oriented commands matching the existing propose, implement, and watchdog roles rather than generic state-machine or GitHub operations.
- Expected workflow outcomes are structured successful statuses; nonzero exits are reserved for invalid command inputs, invalid setup, unavailable dependencies, and unexpected failures.
- Commands discover the Consumer Repository from its Git root with an explicit adapter override.
- Successful publication removes its private temporary result directory; a failed handoff retains it for same-session repair and explicit later cleanup.
- A repairable deterministic precondition refusal returns `fix_required`, retains the Claim and current Workflow State, and supplies exact repair instructions to the current or next resumed Agent Worker. Result Document prose is not such a precondition; only contradictions without a safe deterministic repair enter Needs Human.
- Submission publication appends the machine-owned `Closes #<issue>` footer to the otherwise opaque agent-authored body so GitHub closes the source issue when the Merge Authority merges it.

## Planned refinement: Execution-specific skills

For #44, compose coherent authored Skill Modules into an Execution Skill tailored to one invocation. The engine selects procedures and binds known references; the worker receives instructions to follow, not generic prose and a facts object to assemble. Use the shared `text/template` renderer for definitions, included skills, and parameterized resources so later procedural variation in skills such as Propose does not require another rendering mechanism.

Implementation is pending. Deliver after #37/#39/#40 and before ADR 0005's behavior redesign; that redesign will adapt the modular sources rather than be implemented as part of #44.

### Consequences

- Implementation and Watchdog startup, including resume and Implement's start alias, return the Execution Skill as Markdown by default, without a JSON envelope or separate facts object. `implement submit`, `implement needs-human`, and `watchdog submit` likewise return Markdown outcomes and applicable instructions by default. Explicit `--format json` remains available for programmatic callers; workers give normal Markdown reports rather than forwarding exact CLI output. Authoritative eligibility, Claim handling, and handoff verification remain engine-owned regardless of presentation.
- Both workflow stubs invoke their lane's `next` directly. Plain `skl skill implement` and `skl skill watchdog` retrieval is disabled with guidance to the appropriate workflow command, without implicitly claiming work. Reasoning skills and named resources retain `skl skill` retrieval and applicable stubs. Arbitrary flag-driven standalone Implement/Watchdog generation is future scope.
- Pi's current worker-to-scheduler JSON passthrough and `queue-next.mjs` continuation contract do not constrain shared output design. Explicitly retire or disable incompatible legacy loop entrypoints while preserving normal single-Work-Item Pi invocation. The Pi queue integration redesign is separate work, not a new queue launcher or orchestration framework within #44.
- No-work, idle-timeout, and repair outcomes receive explicit Markdown status and applicable instructions, including briefly telling the user what happened. Do not fabricate a normal execution or imply that an uncertain Claim was released.
- Specialize at the granularity needed for natural instructions, including bundled definitions and later procedural resources. Preserve required invariants, verification, error handling, and genuine future-dependent branches. The engine supplies explicit procedure facts; templates do not infer workflow modes from branch names, comment presence, or incidental field combinations. Included definitions remain loaded once.
- Preserve #40's metadata-only startup boundary. Return every available exact identity, reference, and command within that boundary, but do not add startup project-object/history inspection, including marker discovery through Git logs. Known references are not proof that their contents or ancestry have been validated. Opportunistic startup inspection is deferred, not required by specialization.
- The initial Execution Skill explains how genuinely unavailable facts are acquired after preparation. Necessary later inspection returns narrow specialized instructions or repairs, not another full skill or a requirement to repeat selection. Reuse existing inspection mechanisms where possible, preserve fixed invocation identities, and refresh evidence after worker changes where required. Later inspection is not a reason to withhold facts already established at startup.
- Keep resources deferred until their procedural step. Extend named-resource retrieval with repeated `--input name=value` arguments, not a saved invocation session or a bundle of prerendered resource files. The parent instruction binds every settled argument and names, explains, and constrains only values the worker must establish later. Inputs must not force a decision before the resource needed to make it is disclosed; ordinary agent-authored result prose is not a rendering input.
- Declare resource-specific typed inputs, required status, and help using existing CLI flag types. `--describe-inputs` describes that same contract without rendering the resource. Reject unknown, duplicate, missing required, and invalid inputs while preserving supplied values. The renderer receives ordinary typed inputs, not CLI contexts; no separate schema language or general composition framework is introduced. Context-free resource retrieval remains valid.
- Adapters supply only execution capabilities they can establish, selecting a supported instruction recipe where known. Harness identity alone does not prove tool availability. Retain the small runtime capability choice when genuinely unknown; do not silently force sequential review or invent new harness integrations or a capability registry.
- Present evidence already fetched before handoff once, in labeled evidence sections with its content and provenance preserved. Do not add fetching or move it earlier solely for rendering. Otherwise provide concrete selected-item-bound `gh` retrieval instructions covering required streams, pagination, and failures. Historical artifact reads remain after preparation. External evidence is template data, never template source or replacement workflow instructions.
- Organize modules around coherent procedures, not one file per sentence. Plain definitions need not be split. Internal modules are not public resources. Exact file layout and small parsing helpers remain implementation choices.
- Verify representative complete renderings for initial work, resumed progress, Rework, first review, and repeat incremental/full-fallback review, together with applicable continuations and deferred resources. Use existing tests for required outcomes, input contracts, concrete references, irrelevant-branch removal, deferred disclosure, once-only inclusion, resource visibility, explicit JSON output, and clear retirement or disabling of incompatible Pi loop entrypoints. Preserving Pi's current result-forwarding contract is not an acceptance criterion. No agent benchmark or exhaustive combination framework is required.
- This changes instruction delivery and specialization, not engine-owned Claims and transitions, judgment obligations, or the human merge boundary. ADR 0005's testing and integration redesign remains separate.
